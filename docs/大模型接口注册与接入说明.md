# Trident 大模型接口注册与接入说明

本文供后续开发人员接入、注册、切换和排查大模型接口使用。当前主链路基于 OpenRouter 的 OpenAI-compatible `/chat/completions` 接口。

## 1. 当前架构

```text
backend/.env
  └─ OPENROUTER_API_KEY
        │
backend/src_python/config.py
  ├─ AI_MODEL_ROSTER（可选模型注册表）
  ├─ DEFAULT_AI_MODEL_ID（默认模型）
  └─ backend/runtime/ai_model.json（运行时选择）
        │
        ├─ API Server
        │   ├─ GET /api/ai/models
        │   ├─ PUT /api/ai/models
        │   └─ POST /api/agent_chat
        │
        ├─ AI Worker
        │   └─ 每个新闻批次读取一次当前模型
        │
        └─ Frontend Header
            └─ 模型下拉框查询和切换模型
```

当前模型选择同时影响：

- 新闻 AI Worker 的新闻分析；
- Data Copilot 的 Text-to-SQL；
- Data Copilot 的查询结果摘要。

运行时切换对下一个新闻批次生效，已经开始处理的批次不会中途换模型。

## 2. 配置文件位置

真实配置文件必须放在：

```text
backend/.env
```

`config.py` 固定从该位置加载配置，不读取项目根目录的 `.env`。

最小配置：

```dotenv
OPENROUTER_API_KEY=你的_OpenRouter_Key
```

注意：

- 真实密钥不得写入源码、测试、文档、日志或 `.env.example`；
- `.env.example` 只能保留空值或占位符；
- 修改密钥后需要重启 API Server 和 Engine；
- 运行时切换已注册模型不需要再次重启 Engine；
- 不要把密钥加入 `AI_MODEL_ROSTER`，该注册表会通过 API 返回给前端。

## 3. 注册一个新的 OpenRouter 模型

### 3.1 修改模型注册表

编辑：

```text
backend/src_python/config.py
```

在 `AI_MODEL_ROSTER` 中增加公开模型信息：

```python
AI_MODEL_ROSTER = (
    {"id": "deepseek/deepseek-v4-flash", "label": "DeepSeek V4 Flash"},
    {"id": "vendor/model-id", "label": "前端显示名称"},
)
```

字段说明：

| 字段 | 用途 | 是否可包含敏感信息 |
|---|---|---|
| `id` | OpenRouter 请求使用的模型 ID | 否 |
| `label` | 前端下拉框和日志显示名称 | 否 |

如需将新模型设为默认模型，修改：

```python
DEFAULT_AI_MODEL_ID = "vendor/model-id"
```

默认模型必须存在于 `AI_MODEL_ROSTER`。

### 3.2 确认模型能力

当前 AI Worker 对所有注册模型统一发送：

```json
{
  "model": "vendor/model-id",
  "messages": [],
  "temperature": 0.1,
  "max_tokens": 2048,
  "response_format": {"type": "json_object"}
}
```

注册前必须确认模型支持：

- OpenAI-compatible Chat Completions；
- `messages`；
- `temperature`；
- `max_tokens`；
- `response_format.type=json_object`。

如果模型不支持 JSON mode，不能只修改 roster。需要扩展 roster 的公开能力字段，并在 `build_model_config()` 中按模型设置 `json_mode`。

### 3.3 同步测试

修改：

```text
backend/tests/test_api_events.py
backend/tests/test_engine_core.py
```

至少验证：

- `GET /api/ai/models` 返回新模型；
- `PUT /api/ai/models` 能选择新模型；
- 未注册模型仍返回 HTTP 400；
- `build_model_config()` 返回正确 ID、label 和 JSON mode；
- API 响应不包含 API Key、Authorization 或 Secret。

前端选项来自模型 API，通常不需要修改前端代码。

## 4. 运行时模型选择

当前选择保存在：

```text
backend/runtime/ai_model.json
```

格式：

```json
{"model_id": "deepseek/deepseek-v4-flash"}
```

该文件由 API 原子写入，不应手工修改，也不应提交到 Git。

读取规则：

- 文件不存在：使用 `DEFAULT_AI_MODEL_ID`；
- JSON 损坏：使用默认模型；
- 模型未注册：使用默认模型；
- 多个切换请求同时发生：最后一次成功写入生效。

建议将以下路径加入 `.gitignore`：

```gitignore
backend/runtime/
```

## 5. 模型管理 API

### 5.1 查询模型

```http
GET /api/ai/models
```

响应：

```json
{
  "models": [
    {
      "id": "deepseek/deepseek-v4-flash",
      "label": "DeepSeek V4 Flash"
    }
  ],
  "selected": "deepseek/deepseek-v4-flash"
}
```

### 5.2 切换模型

```http
PUT /api/ai/models
Content-Type: application/json

{
  "model_id": "deepseek/deepseek-v4-flash"
}
```

成功返回最新模型列表和当前选择。

未注册模型返回：

```http
HTTP/1.1 400 Bad Request
```

生产环境注意：当前 PUT 接口没有应用层鉴权。若 API 暴露到不可信网络，必须在 Nginx、网关或应用层增加管理员鉴权，防止未授权用户切换模型或引发额外费用。

## 6. AI Worker 调用过程

主要实现：

```text
backend/src_python/engine/ai_worker.py
```

### 6.1 模型配置构造

`build_model_config(model_id)` 将 roster 中的公开模型信息转换为内部请求配置：

```python
{
    "id": "...",
    "label": "...",
    "api_base": OPENROUTER_BASE_URL,
    "api_key": OPENROUTER_API_KEY,
    "json_mode": True,
}
```

`MODELS` 只是历史兼容导出，不代表当前运行时选择。新代码应使用：

```python
get_current_model_config()
```

### 6.2 动态切换时机

Worker 每次认领一个新闻 batch 后调用一次 `get_current_model_config()`，整批新闻使用同一模型。

因此：

- 切换后不需要重启 Engine；
- 切换对下一批生效；
- 当前批次保持一致；
- Engine 启动横幅不是实时状态，权威状态应查看 `/api/ai/models` 或批次日志。

### 6.3 请求和重试

请求地址：

```text
{OPENROUTER_BASE_URL}/chat/completions
```

请求头：

```http
Authorization: Bearer <OPENROUTER_API_KEY>
Content-Type: application/json
```

当前只对 HTTP 429 重试，退避为 5、10、20 秒。以下错误不会自动重试：

- 401：密钥无效或账户不可用；
- 403：权限、区域或隐私策略限制；
- 404：模型 ID 或 provider 不可用；
- 400：参数或 JSON mode 不兼容；
- 5xx、网络超时和连接失败。

单条新闻调用异常会被归类为失败并将新闻标记为 `FAILED`，不会保存为正常 HOLD 决策。

## 7. Data Copilot 调用过程

主要实现：

```text
backend/src_python/api_server.py
```

`POST /api/agent_chat` 包含两次 LLM 调用：

1. 用户问题转只读 SQL；
2. 查询结果转中文摘要。

当 `OPENROUTER_API_KEY` 存在时，两次调用都优先使用：

- `OPENROUTER_BASE_URL`；
- `OPENROUTER_API_KEY`；
- 当前运行时选择的模型 ID。

旧的 `AGENT_LLM_*` 和 DeepSeek 直连参数仅作为兼容 fallback。当前实现存在一个限制：如果没有 OpenRouter Key 而使用 DeepSeek 直连，动态模型仍可能返回 OpenRouter 风格 ID，导致 endpoint 和模型 ID 不匹配。新增开发应优先修正为“provider、base URL、key 和模型 ID 成对选择”。

SQL 安全要求：

- 只能执行只读 SELECT；
- 禁止系统表和管理命令；
- 后续开发建议统一复用 `db.assert_readonly_sql()`，不要维护第二套弱化规则。

## 8. 接入其他 OpenAI-compatible 厂商

当前 roster 默认把所有模型都绑定到 OpenRouter。接入其他厂商时，仅增加模型 ID 不够。

至少修改：

```text
backend/src_python/config.py
backend/src_python/engine/ai_worker.py
backend/src_python/api_server.py
.env.example
backend/tests/test_config.py
backend/tests/test_engine_core.py
backend/tests/test_api_events.py
```

推荐将公开 roster 扩展为：

```python
AI_MODEL_ROSTER = (
    {
        "id": "public-selection-id",
        "label": "显示名称",
        "provider": "vendor_name",
    },
)
```

然后在服务端内部建立 provider 配置映射：

```python
PROVIDER_CONFIGS = {
    "openrouter": {
        "base_url": OPENROUTER_BASE_URL,
        "api_key": OPENROUTER_API_KEY,
    },
    "vendor_name": {
        "base_url": VENDOR_BASE_URL,
        "api_key": VENDOR_API_KEY,
    },
}
```

不得把真实 key 放进会由 `/api/ai/models` 返回的对象。

同时应让统一解析函数返回成对配置：

```python
{
    "request_model_id": "厂商实际模型 ID",
    "label": "显示名称",
    "provider": "vendor_name",
    "api_base": "...",
    "api_key": "...",
    "json_mode": True,
}
```

AI Worker 和 Data Copilot 必须复用同一解析函数，避免出现：

- OpenRouter endpoint + 其他厂商模型 ID；
- 其他厂商 endpoint + OpenRouter 模型 ID；
- 已选择厂商 B，但因为厂商 A 的 key 存在而仍请求厂商 A。

## 9. 前端模型选择

实现位置：

```text
frontend/components/quant/dashboard-header.tsx
```

流程：

1. 页面加载时 GET `/api/ai/models`；
2. 使用响应动态生成下拉选项；
3. 用户切换后 PUT `/api/ai/models`；
4. 保存期间禁用控件；
5. 请求失败时回滚到原选择。

API 地址来自：

```dotenv
NEXT_PUBLIC_API_URL=http://127.0.0.1:8000
```

生产环境使用 Nginx 同源代理时可留空。

当前前端不会轮询模型状态。其他浏览器切换模型后，已打开页面需要刷新才能同步显示。

## 11. 常见错误排查

### 401 Unauthorized / User not found

检查：

- Key 是否复制完整；
- Key 是否已撤销或删除；
- API Server/Engine 是否在密钥更新后重启；
- 是否误把 OpenRouter Key 配到 DeepSeek 直连 endpoint；
- 请求头是否为 `Authorization: Bearer ...`。

不要在日志或工单中粘贴完整 Key。

### 403 Forbidden

检查：

- OpenRouter 隐私策略；
- Provider 允许列表；
- 区域限制；
- 模型是否要求数据保留策略；
- 代理出口区域。

### 404 No providers / Model not found

检查：

- 模型 ID 是否与 OpenRouter 控制台一致；
- Key 的 provider 限制；
- 模型是否已下线；
- 是否把厂商直连模型名当成 OpenRouter ID，或反之。

### 400 response_format 不支持

模型可能不支持 JSON mode。应按模型能力关闭 `json_mode`，不能依靠 429 重试解决。

### 429 Rate limit

当前 Worker 会自动执行 5、10、20 秒退避。持续 429 时检查：

- OpenRouter 余额和限额；
- 模型 provider 的速率限制；
- `BATCH_SIZE` 和 `_LLM_SEMAPHORE`；
- 是否有多个 Engine 实例同时运行。

### 连接超时

检查：

- `HTTP_PROXY` 是否确实可用；
- `.env.example` 中的本地代理值是否被直接复制；
- 防火墙、DNS 和代理出口；
- 启动日志显示代理不代表请求一定使用代理，当前 Worker 只读取大写 `HTTP_PROXY`。

## 13. 已知技术债

后续维护建议优先处理：

1. 将 provider、base URL、key 和请求模型 ID统一解析，消除 Data Copilot fallback 错配；
2. 为模型注册增加 JSON mode、timeout、额外 headers 等能力字段；
3. 给 `PUT /api/ai/models` 增加鉴权；
4. 将 `backend/runtime/` 加入 `.gitignore`；
5. Data Copilot 统一使用 `db.assert_readonly_sql()`；
6. 修正 AI Worker 代理环境变量大小写不一致；
7. 删除或更新 Kimi K3、Doubao 等过时注释和历史变量名；
8. 补充 Data Copilot、429 重试、provider 配对和响应脱敏的离线测试。
